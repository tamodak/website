# Protocol design

Why is the pairing protocol built the way it is, and where did the specification change the
original design? (§5.1, §5.2, §16)

[`protocol/SPEC.md`](../protocol/SPEC.md) is normative: it fixes the bytes, and where it and
anything else disagree, it wins. This page keeps the reasoning from the design (PLAN.md), which the
specification doesn't repeat. The user-facing ceremony is in
[`../Killit/docs/pairing.md`](../../Killit/docs/pairing.md) §4.

## §5.1 Keys per phone

| Key | Where | Purpose |
|---|---|---|
| `sign` (P-256 ECDSA) | **Android Keystore**, StrongBox, else TEE; never exported | signs every request, answer and pairing statement, and authenticates API calls. It's the authority key, so it lives in hardware. |
| `enc` (X25519, HPKE) | software, in a **Google Tink** keyset encrypted by a Keystore AES-GCM key | decrypts the messages to this phone. Keystore key agreement (`PURPOSE_AGREE_KEY`) needs API 31 while minSdk is 26, so hardware agreement isn't available everywhere. Leaking this key would expose message *contents*, never authority. |

A signing key can't be regenerated silently. If Clear data or a reinstall makes a guardian lose its
keys, the protected phone rejects that guardian's signatures, and the pair pairs again. A protected
phone's keys are protected by the Clear-data hardening.

## §5.2 Message construction

**Sign, then encrypt.** The original design:

```
inner  = kind ‖ version ‖ requestId(16B) ‖ senderFp ‖ recipientFp ‖ body(kind-specific) ‖ createdAt
sig    = ECDSA-P256(sign_key_sender, "KILLIT-MSG-v1" ‖ inner)
env    = HPKE-seal(enc_pk_recipient, info="KILLIT-ENV-v1" ‖ senderFp ‖ recipientFp,
                   pad_to_bucket(inner ‖ sig))
```

- **The kind of request lives inside the ciphertext.** The server can't tell an unlock from an
  unblock or an unpair.
- **Padding** keeps message sizes from giving the kind away. (The specification went further: one
  size for every message, §16.1.)
- **An answer binds** the request id, the requester and signer fingerprints, the kind, the target
  (package and certificate, or the pair id) and the verdict. The protected phone rebuilds those bytes
  from **its own stored request**, never from what the answer claims, verifies them against the
  stored guardian key, and consumes a request id exactly once. That stops replay across requests,
  phones, apps or reinstalls, and stops one guardian being counted twice.
- A request goes out as one envelope per guardian.

Every signed, hashed or MACed structure starts with its own domain-separation label. That's the
lesson of the QR pairing Killit had before (2026-09-28): signed bytes must bind their purpose, a
nonce, the requester and the signer, and both ends must build them from one shared specification.

## §16 The specification and its test vectors

- `protocol/SPEC.md` covers the encoding rules, keys and fingerprints, request signatures,
  registration and key attestation, the invite ceremony, links, the mailbox, push, the envelope, and
  the body of every message kind.
- `protocol/vectors/` holds the test vectors, generated by the reference implementation in
  `protocol/src/`. The server's tests run against them, and Killit's tests must reproduce them. Each
  vector states the outcome it was written to show, and the generator refuses to write one the
  implementation disagrees with. If the text and a vector disagree, both are fixed before anything
  ships.
- **Decoding is total and strict** (L1): every decoder returns a validated value or a rejection and
  never throws past its boundary. That's what makes fuzzing the decoders possible.
- **Version 1 is edited in place until Killit's first release** (K5). After that, a breaking change
  bumps the header byte, the `-v1` labels, the bundle version and the `/v1` API together.

## §16.1 Where the specification refined the design

The specification settled details PLAN.md left open, and changed a few it had sketched:

1. **Fingerprints** are a full SHA-256 of the labelled signing key (32 bytes), never truncated, so
   finding a collision is out of reach.
2. **Every structure starts with its own domain-separation label**, and every message carries a
   **pair id**: a hash of the pairing ceremony's transcript. Messages from an earlier pairing between
   the same two phones can never be replayed into a newer one.
3. **The message header order** is `version ‖ kind ‖ messageId ‖ pairId ‖ senderFp ‖ recipientFp ‖
   createdAt ‖ body`: the fixed fields come first.
4. **One padded size for every message** (an 8 KiB plaintext, an 8240-byte envelope) instead of 1 KB
   and 4 KB buckets. The server accepts nothing else, so sizes say nothing about kinds.
5. **Icons are 32 × 32 raw RGBA pixels**, so no image decoder ever parses network input (libwebp's
   CVE-2023-4863 is the reason). App lists later used 16 × 16 (O1).
6. **CANCEL is part of STATUS**, which also carries the other guardians' decisions (G10): a request
   has one message for "what's the state now".
7. **Roles never reach the server.** The creator's role travels in the end-to-end pairing offer, and
   the joiner declines it if it conflicts with the role the joiner chose.
8. **Decisions are verified against the protected phone's stored request** (§5.2): the signed bytes
   are rebuilt from the stored request, and only the verdict and the note are read from the message.
9. **Request signatures bind the API host**, so a request signed for the test server can't be
   replayed against production.
10. **Registration is itself a signed request** with the newly attested key, which proves the caller
    holds it. Verification mirrors Google's own verifier, including the chain-extension check and the
    factory-key exception for expired certificates.
11. **The server stores no encryption key and no link signatures.** Phones exchange encryption keys
    in the ceremony, signed by their signing keys. Links are plain rows that are deleted, not marked
    removed, and "last seen" is stored as a date only.
12. **The mailbox has no cursor.** Unacknowledged messages are simply delivered again, in the order
    received, and the phone's message-id check drops the duplicates.
13. **Invites live 15 minutes to be joined, then 15 more to finish**, and both phones follow them
    with a long poll.
14. **The test server accepts the debug signing certificate, and a local development server can
    accept emulators.** The latter needs `KILLIT_ENV=development` plus an explicit setting that the
    test and production servers refuse to start with.
15. **A move is a ceremony** (SPEC.md §6.5). The first message after the link is a pairing offer for
    a pairing and a move request for a move, and a phone that receives the other one ends the
    ceremony without either.
16. **The old phone's state travels in pages**, like an app list, and the new phone checks the whole
    before it answers. It keeps the state staged, and puts it in use only once the old phone commits,
    after every HANDOVER has gone out.
17. **A HANDOVER is signed with the old key**, which is what vouches for the new one. The pair id,
    names and counters stay; the new key gets a new badge, as it should.
18. **The server copies links for a move** (SPEC.md §7). It learns which phone handed its links to
    which, and nothing about the pairings.
